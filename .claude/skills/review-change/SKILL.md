# /review-change

1. **收集**：`git status --short`、`git diff`、`git diff --cached`、未跟踪文件。逐个判断是否在本次任务范围内，范围外的单独标出，不混进清单。
2. **自查**：改动里出现用户名、绝对路径、邮箱等本地标识就先改掉。新建的 `.cs` 还没有 `.meta`，说明 Unity 未刷新，提醒用户切回编辑器一下再提交。改过 `.claude/` 或 `ai-docs/` 时先跑 `python .claude/skills/evolution/gc_scan.py`，失效引用修完再列清单。
3. **收尾门**：下辖两项，每项要么有产出、要么在清单里明说「没有」——两样都没有就是那道门被跳过了。

   **3a 埋点门**：本次改动动了 `Assets/_Project/Scripts/Runtime/<模块>/` 下的 `.cs` 才做，没动玩法模块整项跳过、一个字都不用写。
   对涉及的每个模块跑 `python .claude/skills/instrument-module/scan.py <模块>`，看「应埋未埋」那块。
   **只补本次 `git diff` 新增或改到的代码对应的点**；模块里历史遗留的候选点这次不开工，想补另开 [`/instrument-module <模块>`](../instrument-module/SKILL.md) 专门做——否则每次提交都要背一遍全模块的债，这道门很快就会被跳过。
   该补的按 `/instrument-module` 的流程补，**判据是 [`docs/telemetry.md`](../../../docs/telemetry.md) 2.2 的四类尺子，这里不重写**；补出来的改动一并进第 4 步清单待审。
   **没有就明说「本次未动玩法模块」或「新增代码无该埋未埋的点」**，和下面那句「本次无新结论」一样是合格产出。

   **3b 沉淀门**：本次会话有没有**会改变下次决策**的结论？判据只有一句——
   > 不写下来，下次谁会踩什么亏？

   答得出才写。答不出的不写；「这次跑通了」「测试全绿」不是结论；代码注释、提交信息、仓库本身已经讲清楚的也不写。
   该写的按类型落位，**落点与写法直接用 [`/learn` 的沉淀路由表](../../commands/learn.md)，这里不重写判据**。
   **没有就在清单里明说「本次无新结论」，绝不为走流程硬凑一条**——往 `pitfalls.md` 灌水比不写更坏，它会稀释真正重要的那几条。
   沉淀产生的改动一并进第 4 步的清单待审，不偷偷写。
4. **列清单**：一张表，三列：文件路径 | 位置（类 / 方法或行范围）| 改了什么（一句话）。表下给拟用的完整提交信息（标题 + 正文），按 `docs/commit-convention.md` 写；清单里混了多类改动（feat 与 fix）就拆成多次提交，分别给信息。
5. **停下等授权**。「看过了」「流程没问题」都不是授权，只有用户明确说提交才进入下一步。
6. **提交**：`git add` 清单里的文件，用第 4 步给出的提交信息提交。不带任何 AI 署名或会话链接。不 push，除非用户明说。

## 收尾门的载体锚定（3a / 3b 共用）

- **执行载体**：`/review-change` 自身（`CLAUDE.md` 硬规则 4 强制每次提交前走，已证明在运转）。不设周期、不靠谁想起来。
- **状态锚点**：看本次清单——埋点要么有补点条目、要么有那句「未动玩法模块 / 无该埋的点」；沉淀要么有沉淀条目、要么有「本次无新结论」。哪一项两样都没有 = 那道门被跳过了。
- **退场条件**：**埋点门**——连着多次都写「无该埋的点」，而事后 `/analyze-telemetry` 老是因为缺埋点查不动 → 判据太松，收紧它；反过来每次都在补一堆无关紧要的点、或 `scan.py` 误报率高到人人跳过 → **删掉这道门**，四类尺子留给 `/new-feature` 和人工。**沉淀门**——连着多次都写「本次无新结论」，而事后 `/learn` 或用户还能捞出本该沉淀的东西 → 判据没起作用，**删掉这道门**而不是加提醒；反过来 `pitfalls.md` 开始出现凑数条目，同样是删。

## 并发会话

同一个仓库上同时开着另一个会话时，工作区里混着两家的改动，**整份 `git add` 会把对方没审过的内容一起提交**。
归属**按内容判，不按文件名判**（对方给服务加埋点会改到 `UIService.cs`、`developer-guide.md`、`pitfalls.md`，名字里都看不出来）。
混合文件的拆分办法（`git show HEAD:` 取基线 → 只重放自己的改动 → `hash-object` + `update-index` 单独入索引）
与提交前后的兜底检查，见 [`ai-docs/pitfalls.md`](../../../ai-docs/pitfalls.md) 里「两个会话共用一个工作区」一条。

完成标准：清单已列出（两道收尾门各有条目，或各有那句「没有」）并停下；或授权后提交完成并回报 commit hash。

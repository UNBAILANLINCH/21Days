# PRD: 日志回放系统（Replay）

> 阶段：PRP 阶段 1 产物。范围为**期 0 确定性内核 + 期 1 编辑器录制回放最小闭环**。
> 期 2（Android 真机 / seek 拖时间轴 / 自由相机 / 埋点叠加）本次不做，但格式与分层要为它预留。
> 立项日期 2026-09-16。

## 问题 / 动机

QA 或玩家报 bug 时，手上只有一句「卡住了」和几张截图。现有埋点体系能给出事件序列与错误上下文
（`core.log/unity_error` 已是根因分析主线索），但它给不出两样东西：**当时玩家按了什么**、
**当时世界是什么样**。结果是开发者花在「先复现出来」上的时间远多于花在修复上的时间，
而偶现 bug 往往根本复现不出来，只能挂着。

要的是：把一次游戏过程完整留存下来，在编辑器里原样重跑——能看到现场，更重要的是**能断点、
能逐步走、能改完代码重跑验证修没修对**。

为什么是现在：工程玩法未定，`Runtime/` 下只有 Sample 示例。让逻辑变得可重放，
90% 的工作量不在「录制/回放」本身，而在**让游戏逻辑一开始就不引入不确定来源**。
现在定这些约束几乎零成本；等玩法铺开再改，逻辑与表现的耦合会让改造变成推倒重来。

这是**开发工具，不是玩法功能**，面向开发者与 QA。

## 目标（可度量）

- **G1 留得下**：编辑器内一次游戏过程可被完整录制成单个回放文件；5 分钟录制体积 ≤ 2 MB。
- **G2 放得准**：同一份构建下重放一份录制，全程状态哈希与录制时**逐点一致**（漂移率 0）。
- **G3 不拖慢**：开启录制后逻辑帧耗时增加 ≤ 0.2 ms/帧，稳态每帧零 GC 分配。
  （0.2 ms 是初始预算，期 1 实测后回填真实值。）
- **G4 用得起**：从「拿到回放文件」到「在编辑器里看到现场重演」≤ 3 步操作。
- **G5 查得动**：重放中可暂停、逐 tick 步进、变速（0.25× ~ 8×），当前 tick 号始终可见。
- **G6 漂移不瞎**：重放与录制对不上时，能报出**首次漂移的 tick 号**，并自动从最近快照续跑，
  而不是静默播错或直接中断。

## 范围 / 非目标

### 做 —— 期 0（确定性内核，不含录制）

- 逻辑以**固定步长**推进，与渲染帧率解耦；tick 号是全系统对齐的基准。
- **确定性随机数来源**：种子可记录，内部状态可存取与恢复。
- 每 tick 一次的**输入采样**，采样结果是可序列化的命令数据，玩法只消费命令、不直接读设备。
- **数学运算薄封装层**：玩法只经它做数值运算，内部实现当前用浮点，为将来换定点数留唯一改动点。
- 模块提供「世界状态」**序列化与哈希**的统一约定（框架只管收集与编排，状态内容由模块自己定义）。
- 两条硬约束写进架构文档并配 lint 护栏：**逻辑与表现分层**、**物理不参与玩法判定**。

### 做 —— 期 1（编辑器录制回放最小闭环）

- **环形缓冲常驻录制**：只保留最近一段时间（默认 5 分钟，可配），不无限增长。
- **三种保存触发**：未捕获异常 / 错误日志自动保存、热键手动保存、代码 API 保存。
- **单文件回放格式**：头部含格式版本、构建版本、运行平台、随机种子、配置表哈希、起始完整快照。
- **三层记录**，体积依次递增：每 tick 记输入命令 → 每隔固定 tick 记世界状态哈希（用于查漂移）
  → 每隔更长间隔记完整世界快照（用于续跑与将来的 seek）。
- **编辑器回放窗口**：加载文件、播放 / 暂停、逐 tick 步进、变速、显示当前 tick 与漂移状态。
- **漂移检测与从快照续跑**。
- **Sample 模块示范实现** + Showcase 验证场景，保证本期交付**现在就能跑能测**，而不是等玩法的空壳。

### 不做（本次）

| 不做 | 原因 |
| --- | --- |
| Android 真机录制与回传 | 期 2。格式头部预留平台字段、记录分层已按它设计，届时**不改格式版本** |
| Android「一键分享回放」 | 期 2，**与 Android 录制同批做，不可拆分**。Android 11（API 30）起 Scoped Storage 生效，`Android/data/<包名>/` 对第三方文件管理器不可见——**文件存了玩家也拿不出来**，光有录制等于没有。做法：`Intent.ACTION_SEND` + FileProvider，玩家点一下经系统分享面板发出来；按「平台差异只在框架层」扩 `IPlatformService`，玩法层不感知。期 1 不做的唯一理由是那时还没有 Android 录制，没有东西可分享 |
| 拖时间轴 seek、自由相机 | 期 2。完整快照是它的前提，本期已经在录 |
| 回放时间轴叠加埋点事件 | 期 2 |
| 定点数与自写碰撞 | 视期 2 真机漂移数据再评估；现在玩法未定，上了是盲猜 |
| 上传通道 / 网络 | 项目明确不做网络层（architecture.md 第 7 节）。回放文件人工收集 |
| 回放中热重载代码 | 改代码后重新起一次重放即可，不值得为此加复杂度 |
| 玩家可见的回放功能（分享、观战） | 这是开发工具。真要做是另一个 PRD |

## 关键场景（此处「玩家」= 开发者 / QA）

- 作为 **QA**，我在编辑器里玩到一个卡死，游戏自己提示「已保存回放」，我把文件贴进 bug 单——
  不用再回答「你到底怎么操作的」，因为答案在文件里。
- 作为**开发者**，我拿到回放文件，在编辑器里打开回放窗口按播放，看到和 QA 完全一样的过程；
  在怀疑的那行下断点，逐 tick 步进走到出问题那一刻。
- 作为**开发者**，我改完代码重跑同一份回放：bug 不再出现、且修复点之前的状态哈希全程一致，
  我就确信修对了——而不是「我这儿跑了几次没复现」。
- 作为**开发者**，重放报了漂移并指到某个 tick，我立刻知道那段逻辑里混进了不确定来源
  （用了系统随机 / 读了渲染帧时间 / 让物理参与了判定），tick 号直接指向可疑代码。
- 作为**框架维护者**，新人写玩法模块时手一滑写下系统随机，lint 在保存的那一刻就拦住他，
  而不是三个月后在一份放不出来的回放里发现。

## 验收标准

> 对账于 2026-09-16。证据一律是**实测输出**，不是「应该可以」。
> EditMode 173/173、PlayMode Showcase 2/2、lint 零违规、依赖不变量与开工基线一致（均由主窗口复跑确认）。

- [x] 逻辑推进步长固定、与渲染帧率无关 —— 10 FPS 与 200 FPS 喂同样总时长，推出同一串 tick（EditMode，钉死绝对值 70，防「两边都推 0 个」也算通过）
- [x] 同一种子下随机序列可重现；随机状态存取并恢复后，序列与未中断时相同 —— EditMode；另有 Python 独立实现跑出的黄金序列逐位比对
- [x] 输入命令序列化后反序列化，逐字段相等 —— EditMode；定长 31 字节，带 offset 写入不污染相邻字节
- [x] 一段录制在同一构建下重放，全程状态哈希逐点一致（G2）—— Showcase 实测 **0 次漂移 / 15 个校验点**，末态 106 字节逐位相同
- [x] 注入不确定来源后报出**首次**漂移 tick 号 —— Showcase 实测 `FirstDriftTick=120`（注入点 100 之后的第一个校验点，最后一个校验点在 840）；EditMode 另有专项用例
- [x] 漂移后从最近完整快照续跑，回放不中断（G6）—— Showcase 实测拉回 1 次后跑到 tick 900 终点
- [x] 稳态录制每帧零 GC 分配（G3）—— 多处实测：录制 2 万 tick、状态序列化 2 万轮、chunk 读写各 2 万条，托管堆增量**均为 0 字节**
- [~] 未捕获异常触发时回放文件落盘，**且能被回放窗口加载** —— 前半截已验（自动保存触发、重入防护、落盘后能被 `ReplayReader` 读回）；**「被窗口加载」这一步没有端到端验证**，见下方说明
- [x] 头部含格式版本；版本不匹配给可读报错，不崩溃不静默播错 —— 实测 14 例头部损坏，报错能说出断在**哪个字段**上
- [~] 回放窗口可暂停、逐 tick 步进、变速，当前 tick 号可见（G5）—— **播放器层全部验过**（暂停不推进、单步精确推 1、0.25~8 倍速）；**窗口 UI 的真实交互没验证**，见下方说明
- [x] lint 对逻辑层的系统随机 / 渲染帧时间 / 物理判定报违规 —— 5 条规则，探针实测 4 BLOCK + 1 WARN 全部命中，且不误伤 `Core/` 与 `Sample`
- [x] `/verify-module replay` 跑通并出报告 —— PlayMode 2/2，报告在 `Logs/verify/replay/latest.md`，含 2 张截图
- [x] 5 分钟录制体积 ≤ 2 MB（G1）—— 见下方实测回填

### 两条未完全达成的说明（不算通过，如实记）

**窗口 UI 的真实交互没有端到端验证。** 验过的是：窗口能开、菜单项在、非 Play 与拿不到播放器时的降级路径不抛异常、以及它调用的那条容器解析路径（Showcase 在真实容器里验过 `TryResolve` 能解析出播放器与录制器）。**没验的是**：人在窗口里选一个回放文件、按播放、看着 tick 走、拖速度条——这一段需要人在编辑器里手动操作，自动化测试覆盖不到。

这两条的共同点是**都卡在"编辑器窗口的人工操作"这一段**，而底下的播放器逻辑全部验过。建议的收尾动作：手动跑一次「进 Play → 录一段 → 触发保存 → 开窗口载入 → 播放/步进/变速」，五分钟的事，做完这两条才算真的合格。

### 实测回填

| 指标 | PRD 目标 | 实测 | 说明 |
| --- | --- | --- | --- |
| 录制体积 | 5 分钟 ≤ 2 MB | 约 **690 KB**（外推） | Showcase 实录 900 tick = 34692 字节，按 60 tick/s 外推 5 分钟。**前提**：该世界状态仅 106 字节（6 个实体）。真实玩法状态更大时，吃体积的是完整快照（默认每 600 tick 一次），输入流部分恒为 31 B/tick |
| 稳态 GC | 每帧零分配 | **0 字节** | 多路径实测，见上 |
| 逻辑帧耗时增量 | ≤ 0.2 ms/帧（初始预算） | **未实测** | 当时写明「实测后回填」。本期只在一帧内推完几百 tick 的压测场景下验过零分配，没有单独测过「开启录制 vs 关闭录制」的逐帧耗时差。要准确回填需要接一个真实玩法模块后用 Profiler 对比 |

## 涉及模块 / 依赖

| 位置 | 内容 | 说明 |
| --- | --- | --- |
| `Scripts/Core/`（`Game.Core`） | 固定步长推进、随机数服务、输入命令采样、数学封装、世界状态约定、录制与回放编排 | **零玩法**，属框架设施，因此归 Core 而非 `Runtime/<Module>/` |
| `Scripts/Editor/Tools/`（`Game.Editor`） | 回放窗口 | 已有 `Tools/` 目录与多个工具窗口可参照 |
| `Scripts/Tests/EditMode/`（`Game.Tests.EditMode`） | 确定性、序列化、漂移检测的断言测试 | 优先 EditMode |
| `Scripts/Tests/Showcase/Replay/`（`Game.Tests.Showcase`） | 录制→重放的回放验证场景 | 走 `/verify-module` |
| `Runtime/Sample/`（`Game.Runtime`） | 世界状态序列化与哈希的示范实现 | 见 Q6 |
| `Data/`（新建 ScriptableObject） | 录制开关、缓冲时长、快照间隔、哈希间隔 | 参照 `TelemetryConfig.asset` 的形状 |
| `.claude/skills/project-lint/rules.json` | 两条硬约束的护栏规则 | 数据驱动，加规则不改代码 |

**契约变更**（`architecture.md` 要求「改动其中任何契约先说明理由」）：

- 输入服务契约：现在直接把生成的动作集交给玩法（5.8），这条路**录不到任何东西**，
  需要补一层每 tick 采样成命令的入口。
- 时钟契约：`IClock`（5.8）包装的是渲染帧时间，无 tick 概念，需在其旁增加逻辑时钟。
- 配置契约：配置表改动后再放旧回放必然全程对不上，需要一个内容指纹才能把这类失败
  报成「配置版本不匹配」而不是一堆漂移点（PRP 阶段 3 校验时发现，现有配置服务没有任何此类概念）。
- 第 7 节「联网只留缝」表格补一行：确定性内核同时也是将来帧同步联机的地基。

**外部依赖**：不引入新包（序列化方案见 Q3）。无新场景（Showcase 场景可代码搭）。

## 已定决策（2026-09-16）

原为待确认项，逐条判定如下。均为参数或局部选择，无方向性分叉；有异议改这里再重走 PRP。

- **D1 环形缓冲默认 5 分钟**，写进配置可调。理由：bug 的起因极少在 5 分钟之前；
  按每 tick 输入几十字节估算，5 分钟常驻内存在 1 MB 量级，够便宜。真不够用时调大配置即可，
  不需要改设计。
- **D2 正式包默认关闭，Development / 内测包默认开启**，均可用配置覆盖。理由：录制是开发工具，
  正式包里常驻既无收益也白担性能与隐私风险；内测包是 bug 的主要来源，必须默认开。
- **D3 自写二进制格式**，不引入 MemoryPack。理由：回放文件要**长期稳定**——半年前的回放
  必须还能放。格式随第三方库版本走，等于把兼容性交给别人；而且自写格式才好配诊断工具
  （坏文件也要能读出头部说清楚坏在哪）。本期数据量下性能不是瓶颈。
- **D4 重放默认静音，可开**。理由：同一段反复重放十几遍，声音是干扰不是信息。
- **D5 做「录制中打点」**。理由：成本极低（一个命令类型 + 一次热键），
  但它让开发者能直接跳到 QA 认为出问题的位置，而不是从头看——对 G4 的提升最划算。
- **D6 示范载体放 Showcase，不动 Sample、不新建玩法模块**。理由：Sample 的职责是
  「示范玩法模块该长什么样」，往里塞 tick 演化与随机数会让它同时背两个职责；
  而玩法未定时新建一个假玩法模块，它注定成为技术债。回放需要的只是一个
  「随 tick 演化 + 用到随机数」的最小世界，放在 `Tests/Showcase/Replay/` 里自给自足，
  验证闭环一样完整，且不污染 `Runtime/`。
  （CLAUDE.md「加能力的顺序」：复用不行——工程内没有随 tick 演化的世界；
  扩展 Sample 不行——职责说不通，且 Sample 不在本次改动范围内。）

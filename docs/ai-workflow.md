# AI 工作流（harness）

这份讲**我们为什么有这套东西、它由什么组成、你日常怎么用它**。
资产清单不写数字（数字会过期），一律指向目录——目录里有什么就是什么。

> 只想知道「我该读哪些文档」看 [`README.md`](../README.md) 顶部的角色导航；
> 只想知道「某个钩子为什么拦我」看 [`.claude/hooks/README.md`](../.claude/hooks/README.md)。

## 一、为什么需要它

AI 写代码在样板、排查、查 API 上已经够用，落到真实工程会撞同一堵墙：**大方向能跑通，精确控制难**。
这不是模型不够聪明，是模型和工程之间缺一层。具体表现为四类：

| 问题 | 在本工程长什么样 |
| --- | --- |
| **约束没投喂** | 不知道我们禁止 `public` 字段、玩法代码里不许出现平台宏、模块状态必须注册进根作用域 |
| **工具够不着** | 代码写完要人去 Unity 里点运行；建物体挂组件赋引用只能靠人 |
| **写完没法验** | 编译过了不代表对，而对错要等人跑一遍才知道 |
| **坑会再踩** | 上次纠正过「Dynamic 字体资产提交前要清动态数据」，换个会话又犯 |

harness 就是补这一层：**把约束按需送到眼前、把工具接进来、给产出建自动反馈、把教训沉淀成可复用资产。**

设计前提是一个硬约束：**上下文窗口有限**。不能把工程全量塞进去，也不该——无关信息会稀释注意力。
所以核心目标不是「让 AI 知道得更多」，而是**让它在每个时刻刚好看到该看的那一份**。

## 二、五层

每层只回答一个问题，互不干扰，可以单独替换。

```
进化层   harness 自己怎么改进？   /learn · /gc · invariants.py · /run-evals
编排层   怎么组织执行？           /dev · /new-feature · PRP 四阶段 · /review-change
策略层   什么必须 / 禁止做？      CLAUDE.md 硬规则 · .claude/rules/ · hooks/ · project-lint · code-reviewer
知识层   Agent 知道什么？         CLAUDE.md · ai-docs/ · 模块三件套 · pitfalls.md · 跨会话记忆
能力层   Agent 能做什么？         .claude/skills/ · Unity MCP · scripts/
```

**层间关系**：编排层读知识层、调能力层、受策略层约束；进化层可以改任何一层。
注意**策略层不「调用」任何层，它只「约束」**——规则不是被查询的，是被钩子和上下文加载机制自动施加的。

### 各层在本仓库的落点

| 层 | 在哪 | 怎么生效 |
| --- | --- | --- |
| 能力层 | `.claude/skills/` | 用户敲 `/名字` 触发；部分技能模型可自动调用 |
| 知识层 | `CLAUDE.md`、`ai-docs/`、全局记忆 | `CLAUDE.md` 每次会话常驻；其余按需读或由钩子提示 |
| 策略层 | `CLAUDE.md` 硬规则、`.claude/rules/`、`.claude/hooks/`、`.claude/skills/project-lint/`、`.claude/agents/` | 规则按 glob 自动注入；钩子在工具调用前后拦截；lint 保存即跑 |
| 编排层 | `.claude/commands/`、部分 skill | 用户触发，产物落 `PRP/<feature>/` |
| 进化层 | `.claude/skills/evolution/`、`evals/` | `/learn` 沉淀、`/gc` 体检、`/run-evals` 验行为 |

## 三、日常怎么用

### 按场景找入口

| 我要做的事 | 走哪 |
| --- | --- |
| 第一次拉到这个工程 | `/onboard`——带你装环境、连编辑器、跑一次测试 |
| 随便什么开发任务，不知道该多正式 | `/dev <任务>`——按复杂度分流：简单直接做 / 中等先出方案 / 复杂走 PRP |
| 新建一个玩法模块 | `/new-feature <模块名>` |
| 跑测试 | `/unity-test [EditMode\|PlayMode]` |
| 出包 | `/build [Windows\|Android]`（编辑器须关闭） |
| 改动做完要提交 | `/review-change`——列清单等审，**授权后才提交** |
| 复杂功能要留决策痕迹 | PRP 四阶段，见 [`PRP/README.md`](../PRP/README.md) |
| 生成 / 同步模块文档 | `/generate-doc <模块>` |
| 踩了坑想让它别再犯 | `/learn` |
| 怀疑 harness 自己坏了 | `/gc` |
| 改完规则想知道 AI 行为有没有真变 | `/run-evals` |

完整命令与技能清单见 `.claude/commands/` 与 `.claude/skills/`，各自的 `SKILL.md` 就是使用说明。

### 会自动发生什么

你不用记，但知道了不会被吓到：

| 时机 | 发生什么 |
| --- | --- |
| 改任何文件、跑命令、派 subagent 之前 | `guard.js` 检查：写生成物直接拒、`git commit` / `git push` 弹确认、派单漏传模型档位拦下 |
| 编辑 `.cs` / 场景 / 预制体之前 | 提示适用的规则；编辑玩法模块前**要求先读过它的 guide**，没读过会拦（用 Read 工具或 `cat` 读过都算） |
| 保存 `.cs` 之后 | `project-lint` 自动跑。**通过时静默**，违规才输出行号、原因、改法 |
| 连续编辑同一个文件太多次 | 提醒可能在错误方向上打转（换文件即清零，跨阶段回来改同一个文件不会误报） |
| 会话结束前 / 上下文压缩前 | 检查残留、保存改动快照 |

注册明细在 `.claude/settings.json`，每个钩子做什么在 [`.claude/hooks/README.md`](../.claude/hooks/README.md)。

### 对你的三条硬要求

1. **提交前必审**：改动攒在工作区，`/review-change` 列清单，**明确授权才提交**。不 push 除非明说。
2. **护栏挡住时不拆护栏**：先看理由。确属误报，在那行写 `// lint-ok: <理由>` 放行，理由必须写。
3. **生成物不手改**：`Library/`、`.meta`、Luban 生成的代码与数据等。钩子会拒，被拒就换做法。

## 四、新增东西时放哪一层

```
1. 在改进 harness 自身吗？        → 进化层
2. 定义多步流程 / 工作流吗？      → 编排层
3. 是约束 / 禁令 / 强制检查吗？   → 策略层
4. 提供参考信息 / 经验 / 记忆？   → 知识层
5. 是具体工具 / 能力 / 集成？     → 能力层
```

横跨多层的按**主要职责**归主层，在别层留一行引用。细则与硬要求见
[`.claude/rules/harness-authoring.md`](../.claude/rules/harness-authoring.md)，其中最重要的一条是**载体锚定**：
新增任何会自己跑起来的东西，必须写明执行载体、5 秒可证伪的状态锚点、退场条件，
给不出载体就显式标注，不假装它会被「记得来做」。

**三类资产别混**：规则说「不要做什么」（约束，按 glob 注入，150 行以内），
文档说「这是什么」（知识，按需读，可以长），技能与命令说「怎么做」（流程与模板）。

## 五、它自己怎么不腐化

这套东西也会烂，所以留了四道机制，**每道都有真载体**（不是日历，不是待办清单）：

| 机制 | 查什么 | 谁触发 |
| --- | --- | --- |
| `/gc` | 失效链接、缺失路径、钩子自测、工程跨文件静态不变量 | 人发起 |
| `project-lint` | 逐文件的代码反模式 | 保存 `.cs` 自动 |
| `/run-evals` | 改完规则后 AI 行为有没有真变 | 改完规则时，`/learn` 收尾会问 |
| `/learn` | 把纠错沉淀成 lint 规则 / pitfalls / 规则 / 记忆 | 踩坑之后 |

沉淀优先级：**能让机器当场拦下的 > 写进文档的 > 靠人记得的**。
同一条约束只放一处——lint 能查的只进 lint，正文里只留一行「关联：lint 规则 `<id>`」。

**不建需要人维护才准确的清单、快照、注册表**。需要全局视图时现扫一遍，重扫比维护基线便宜。
这条是有教训的：参考的那套成熟 harness 里，日历驱动的机制全部停摆，人工维护的清单全部腐烂。

# Evals — 给 AI 行为写的「单元测试」

> `project-lint` 保**单次改动对**，eval 保**整套规则能让 AI 一次做对**。
> 两者不重复：lint 是编辑后的实时防线，eval 是 harness 的回归测试。

## 这是什么

一个 eval case 就是**一个带陷阱的任务提示 + 期望行为**。它检验的不是模型聪不聪明，而是这套 harness（`CLAUDE.md` + `.claude/rules/` + 钩子 + lint + 模块文档）**有没有在正确的时刻把正确的信息送到**，让 AI 不踩那个坑。

改了规则、加了 lint 规则、调了钩子之后，跑一遍相关 case，确认 harness 没有退化。

## case 结构

每个 case 一个 `cases/<名字>.md`，四段：

| 段 | 写什么 |
| --- | --- |
| **场景** | 原样给 AI 的任务提示。要像真实需求那样自然，不能自带提示（不能写「注意别在 Update 里 Find」）。 |
| **陷阱** | 照字面做最容易犯的错，以及它违反了哪条规则。 |
| **期望行为** | harness 生效时应该发生的事，**按防线顺序列**：注入规则 → AI 自己做对 → 万一做错被 lint 拦 → code-reviewer 复查。 |
| **判定** | 可勾选的通过条件。越具体越好，能对应到文件、行为、退出码。 |

## 写 case 的原则

- **一个 case 只验一条规则**，混着验就分不清是哪道防线没生效。
- 陷阱要**真实**：来自 `ai-docs/pitfalls.md` 的真坑，或者已经被纠正过一次的错。
- 判定里要包含**多层防线**：最好的情况是 AI 直接做对，但也要写清「做错时哪道护栏应该拦下」——两条都不成立才算 case 失败。
- 期望行为里不写「AI 应该聪明地想到」，只写「harness 应该让它看到什么」。

## 怎么用（当前为人工评估雏形）

1. 开一个干净会话，把 case 的「场景」原样发给 AI。
2. 观察：钩子提示了吗？读了哪些文档？写出来的代码是什么样？lint 有没有报？
3. 对照「判定」逐条打勾，不通过的记下来——通常说明某条规则没被加载到，或者 lint 规则的正则没覆盖到。
4. 修完 harness 再跑一遍。

规模做大后再考虑自动化：批量跑 + 评分 + 历史对比。现在 case 少，人工跑更快也更准。
